Architecture¶

How the firmware is put together: the layers, the boot table, the system state machine and the supervisor loop.

Figure description and sources

From top to bottom. The ESP-IDF main task runs app_main, which starts the VortexSys orchestrator task and waits for its boot table, then becomes the supervisor loop. VortexSys brings up the HAL, starts the LedDemo thread (WS2812TestThread) and, when menuconfig selects the CANopen device, the co_svc task that serves CoNode (CANopenNode over the generated object dictionary, on the TWAI port). Every task reaches the hardware through the Vortex HAL singleton, which owns the managers, the hf-core handlers and the chip drivers. Stack sizes and priorities are the constants in the sources listed below.

Drawn from: main/app_main.cpp; main/apps/system/sub_threads/VortexSystemThread.h; main/apps/system/sub_threads/VortexSystemThread.cpp; main/apps/node/sub_threads/ws2812/WS2812TestThread.h; main/apps/node/canopen/CanopenDevice.cpp; main/apps/node/canopen/CoSvcFreeRtos.cpp; main/apps/supervisor/VortexSupervisor.cpp; figure module docs/diagrams/figures/firmware-tasks.py.

Layers¶

Layer Where What it owns
Application main/ app_main, the orchestrator, the supervisor, worker threads
Contracts contracts/ Header-only rules (CiA 402, fault policy, routing, store codec, OD ids); no RTOS, no HAL; host-tested, not yet linked into the firmware
Object dictionary od/ vortex_od.yaml and everything tools/odgen generates from it
HAL hal/hf-hal-vortex-v1 (submodule) The Vortex singleton, managers, hf-core handlers, chip drivers, CANopenNode (HAL docs)
Platform ESP-IDF v5.5 FreeRTOS, drivers, the build system

The application is the ESP-IDF main component. The root CMakeLists.txt adds only the HAL to EXTRA_COMPONENT_DIRS; the HAL builds hf-core and the drivers itself. There is no middleware layer: anything shared lives in the HAL.

Boot table¶

VortexSystemThread::Setup() walks kInitSequence in order. A failed step marked recoverable is logged and boot continues; a failed non-recoverable step moves the state machine to Fault, tears down the steps that completed, in reverse order, and makes Setup() return false.

Step Recoverable Setup Teardown
vortex_hal no Vortex::GetInstance().EnsureInitialized() Vortex::Shutdown()
ws2812 yes EnsureInitialized() and Start() of the LedDemo thread Stop()
can_worker yes With menuconfig None: nothing. With CANopen device: StartCanopenDevice() on CommChannelsManager::GetEspCan() StopCanopenDevice()

Adding a step means adding a Setup* / Teardown* pair and a row to kInitSequence[] in VortexSystemThread.cpp. Boot and updates follows the whole sequence from reset.

System state machine¶

VortexSystemStateMachine holds one atomic VortexSystemState and the reason of the last change. TryTransition() stores the new state without a guard table; the states mark milestones for logs.

From To When
(start) Boot Setup() starts
Boot HalInit the vortex_hal step
HalInit ThreadsUp the can_worker step
ThreadsUp Ready every step done
HalInit Fault a non-recoverable step failed
Ready Fault Cleanup()

Supervisor loop¶

After boot, RunVortexSupervisorLoop() runs on the ESP-IDF main task and does not return. It prints a banner, the ESP-IDF version, chip information and Vortex::GetSystemDiagnostics(), then loops every 100 ms:

Period Counter condition Work
2 s count % 20 == 0 Toggle the status LED between STATUS_OK and STATUS_BOOT
5 s count % 50 == 0 Vortex::PerformHealthCheck(); LED STATUS_WARN on failure, STATUS_OK otherwise
10 s count % 100 == 0 Log uptime and free heap; log whether LedDemo runs
20 s count % 200 == 0 GPIO (pulses GPIO_EXT_GPIO_CS_1 high for 200 ms, reads PCAL GPIO17/18), ADC and temperature reads, LED (four status animations, 0.5 s each)
20 s, offset 10 s count % 200 == 100 Motor controller, IMU and encoder demos: handler lookups, device counts, encoder angle and velocity (reads only)

The demos address pins and channels by their HAL names (GPIO_EXT_GPIO_CS_1, ADC_TMC9660_AIN3); the names are in the HAL pin map.

Design choices¶

  • A thin app_main. Boot order and teardown live in one table that can be read top to bottom.
  • Static stacks. VortexSystemThread and WS2812TestThread pass member arrays to CreateBaseThread(); only CANopenNode allocates (CO_new() and an 8192-byte task stack).
  • One owner per bus direction. Only one task may drain BaseCan::ReceiveMessage() on the CANopen bus, which is why the CAN worker is a menuconfig choice with one option at a time.
  • Rules before integration. The CiA 402 and fault tables are written and host-tested in contracts/ before the firmware uses them (design notes).
